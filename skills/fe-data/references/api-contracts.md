# API Contracts & Typed Clients — REST/OpenAPI, GraphQL, tRPC, BFF

The schema is the contract. Types are generated from it, never hand-written; one client module talks to each backend; errors have one shape. Tool names and options below are current as of writing — confirm versions with fe-review before adopting.

## 0. Choose the integration style

| Question | REST + OpenAPI | GraphQL | tRPC | BFF (server-side proxy) |
|---|---|---|---|---|
| Who owns the backend? | Any team / third party | Any team (needs a GraphQL server) | **Same TypeScript team, same repo/monorepo** | Frontend team owns a thin server (Next.js route handlers, Hono, Express) |
| Public or multi-client API? | ✓ best | ✓ | ✗ (TS-only, no public contract) | n/a (internal) |
| Over/under-fetching pain? | Add endpoints / sparse fieldsets | ✓ solved by queries | ✓ per procedure | ✓ aggregate server-side |
| End-to-end types | Generated from spec | Generated from schema + operations | Inferred, zero codegen | Whatever the BFF exposes (REST/tRPC) |
| Caching | HTTP + query library | Normalized client cache | Query library | HTTP + query library |
| Cost | Keep spec accurate; regenerate in CI | Schema design, cache normalization, N+1 on the server | Tight coupling; versioning by deploy order | One more service to run and secure |

Default for a product frontend with a separate backend team: **REST + OpenAPI codegen**. Default for a TS monorepo where one team owns both sides: **tRPC**. Add a **BFF** when tokens must stay server-side (fe-sec auth-frontend.md §6), when several upstreams must be aggregated, or when a third-party API key must not reach the browser.

## 1. Principles (all styles)

1. **Generate, don't transcribe.** Payload types come from the spec/schema in CI; a hand-written `interface Order` is a drift bug waiting to happen.
2. **One client module per backend** (`lib/api/<name>/`): base URL, auth header injection (fe-sec), timeout + `AbortSignal` (SKILL.md §2), error mapping. Features import hooks, never `fetch` directly.
3. **Validate at the trust boundary where types are not enforced at runtime.** Generated types describe what the server *should* send. For money, auth and anything that drives a mutation, parse critical responses with a schema (Zod) at least in development and tests; in production, validate where a wrong shape would corrupt data.
4. **Errors have one shape** (§6). Components never branch on raw status codes.
5. **Cache keys mirror the contract**: `["orders", { page, status }]` for REST; operation name + variables for GraphQL; tRPC derives keys itself.
6. **Contract changes are versioned** (§7) and caught by CI, not by users.

## 2. REST + OpenAPI

| Tool | Generates | Use when |
|---|---|---|
| `openapi-typescript` + `openapi-fetch` | Types per path/method + a tiny typed `fetch` wrapper | Minimal, framework-agnostic default |
| `orval` | Typed client **+ TanStack Query hooks + MSW mocks** from one spec | You want hooks and mocks generated together |
| `@hey-api/openapi-ts` | Client + types, plugin-based (TanStack Query, Zod) | Alternative to orval; check plugin maturity |

```ts
// lib/api/shop/client.ts — openapi-fetch; types generated by `openapi-typescript spec.json -o ./schema.d.ts`
import createClient, { type Middleware } from "openapi-fetch";
import type { paths } from "./schema";

const auth: Middleware = {
  async onRequest({ request }) { request.headers.set("Accept", "application/json"); return request; }, // cookies carry the session (fe-sec)
  async onResponse({ response }) { if (response.status === 401) window.dispatchEvent(new Event("auth:expired")); return response; },
};
export const shop = createClient<paths>({ baseUrl: "/api/shop", credentials: "include" });
shop.use(auth);

// features/orders/queries.ts — path and params are type-checked against the spec
import { queryOptions } from "@tanstack/react-query";
export const ordersQuery = (page: number) => queryOptions({
  queryKey: ["orders", { page }],
  queryFn: async ({ signal }) => {
    const { data, error, response } = await shop.GET("/orders", { params: { query: { page } }, signal });
    if (error) throw toApiError(response, error); // §6
    return data;
  },
});
```

**CI contract gate:** regenerate types from the spec on every pipeline run and fail if the generated file differs from the committed one (`git diff --exit-code`). When the backend publishes a new spec version, the diff *is* the review. Mock the API in tests from the same spec (orval's MSW output or Prism) so mocks cannot drift either.

**Next.js:** call the backend from Server Components/route handlers with the same generated types (`openapi-fetch` works server-side; pass `next: { revalidate, tags }` through `fetch` options). **Vite / plain React:** the client runs in the browser; the base URL is a public env var, auth is cookie-based or via BFF.

## 3. GraphQL

| Client | Pick when | Notes |
|---|---|---|
| **urql** | Default for most apps | Small, document cache by default, normalized cache via `@urql/exchange-graphcache` when needed |
| **Apollo Client** | Large schema, heavy normalized caching, team already on it | Bigger; configure `typePolicies.keyFields` for every entity type |
| **Relay** | Fragment-driven architecture at scale | Steep setup; compiler enforces colocation |

Codegen: `@graphql-codegen/cli` with the **`client` preset** → a typed `graphql()` tag producing `TypedDocumentNode`; hooks infer result and variable types from the document.

```ts
// features/orders/orders.graphql.ts — fragments colocated with the components that need them
import { graphql } from "@/gql";
export const OrderRowFragment = graphql(`fragment OrderRow on Order { id status total { amount currency } }`);
export const OrdersQuery = graphql(`query Orders($page: Int!) { orders(page: $page) { ...OrderRow } }`);
// const [{ data, fetching, error }] = useQuery({ query: OrdersQuery, variables: { page } }); // urql
```

Rules:
- **Fragments colocate** with components; pages compose fragments. No component selects fields it does not render.
- **Normalized cache needs ids**: every entity type exposes `id` (or configure `keyFields`); mutations return the changed entity so the cache updates itself; use `refetchQueries`/cache updates only for list membership changes.
- **Partial data and errors**: decide `errorPolicy` per query; render what arrived, show errors inline for the failed field group.
- **Persisted / automatic persisted queries** reduce payload and lock the allowed operations in production (also a security control: fe-sec).
- **N+1 and complexity limits are server concerns** — ask for DataLoader and depth/complexity limits; the frontend keeps queries shallow.
- **Subscriptions**: WebSocket (`graphql-ws`) or SSE; reconnect and backoff rules in [resilience.md](./resilience.md) §4.
- **Next.js**: fetch in Server Components with a plain POST to the endpoint and the same typed documents; keep the client-side cache for interactive parts only. Framework-specific Apollo/urql SSR integrations change often — verify with fe-review before adopting.

## 4. tRPC

Use when server and client are TypeScript in one repo and the same team owns both. The router type is the contract; there is no spec to publish.

- Prefer the TanStack Query integration (`@trpc/tanstack-react-query` in v11 — verify the package for your version): queries and mutations become ordinary TanStack hooks with inferred types, so all cache rules in SKILL.md apply unchanged.
- Validate every procedure input with Zod on the server; the client types follow.
- SSR/RSC: call procedures through a server-side caller and hydrate the query client; do not fetch through HTTP from the server to itself.
- Limits: no non-TS consumers, no public API, breaking changes ship with the deploy (coordinate server-first rollout, fe-ship).

## 5. BFF (backend-for-frontend)

Keep it thin: auth/session handling, aggregation, hiding third-party keys, shaping responses for the UI. No business rules that belong to the backend.

| Host | BFF shape |
|---|---|
| Next.js | Route handlers (`app/api/**/route.ts`) and Server Actions; server-only env for upstream keys; same-origin cookies, so no CORS and simpler CSRF |
| Vite / plain React | Small Node service (Hono/Fastify/Express) on the same site (`/api` via reverse proxy) with cookie sessions + CSRF token |

Rules: validate inputs (schema), forward only needed headers, set timeouts per upstream, never log tokens, apply the fe-sec header set, and keep BFF endpoints in the same OpenAPI spec so the frontend client stays generated.

## 6. One error shape

Map transport and server errors to a discriminated union once, in the client module:

```ts
export type ApiError =
  | { kind: "network"; retryable: true; cause: unknown }                              // offline, DNS, timeout, aborted
  | { kind: "http"; status: number; retryable: boolean; problem?: ProblemDetails }   // RFC 9457 body when the server sends it
  | { kind: "validation"; fieldErrors: Record<string, string[]>; formError?: string } // 400/422 with field map
  | { kind: "auth"; status: 401 | 403 }                                                // → refresh/login (401) or access-denied state (403), never retried
  | { kind: "schema"; issues: string[] };                                               // response failed runtime validation

export type ProblemDetails = { type?: string; title: string; status: number; detail?: string; instance?: string; errors?: Record<string, string[]> };
```

- `retryable` is true only for network errors, 408/429/5xx on idempotent requests ([resilience.md](./resilience.md) §1).
- The UI switches on `kind`, never on status codes; copy comes from fe-ux ux-writing rules.
- Error tracking receives `kind`, `status`, operation name and request id — never bodies with personal data (fe-ship).

## 7. Versioning and contract evolution

| Change | Rule |
|---|---|
| Add a field / optional param | Safe; regenerate types; consumers ignore unknown fields (do not use strict object schemas on responses) |
| Remove or rename a field, change a type | Breaking: new version (`/v2`, header, or new GraphQL field with deprecation) and a migration window; old field marked `deprecated` in the spec/schema |
| Deprecation | `Deprecation`/`Sunset` headers or `@deprecated` directives; the client logs usage of deprecated operations in dev |
| Feature detection | Branch on the presence of a field/capability in the response, not on app version strings |
| Contract tests | Minimum: generated-types diff gate in CI + schema validation of critical responses in E2E against staging. Consumer-driven contracts (Pact) when several frontends share one backend |

## 8. Verify

- Generated types are committed and the CI regeneration step produces no diff.
- No `fetch(`/`axios` calls outside `lib/api/**` (grep); no hand-written payload interfaces for generated endpoints.
- Changing a field name in the spec breaks the type-check in the feature that uses it (prove once).
- Every error path renders through the `ApiError` union; 401/403 are never retried (network tab).
- Mocks in tests come from the spec/schema (orval/MSW handlers or codegen mocks), not hand-written JSON.
- Deprecated operations are not called in production (server logs or client dev warning).
